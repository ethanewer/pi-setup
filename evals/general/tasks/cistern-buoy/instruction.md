# Fix curl destroying its HSTS cache when a server demands an absurd max-age

## Environment

the clone, and it is the latest upstream revision at which the defect

The project is already configured and built in the image:

- `/app/src/src/curl` — the build output binary (a **debug** build, matching
  the upstream developer setup),
- `/app/src` — the full source, test data and test harness; the test harness

There is **no network** in this container. Everything you need is already on

A quick orientation to the feature this task is about. When `curl` is told to
remember HTTP Strict Transport Security (HSTS) policies (`--hsts <file>`), it
keeps a small cache file on disk, one line per host:

```
# Your HSTS cache. https://curl.se/docs/hsts.html
# This file was generated by libcurl! Edit at your own risk.
somehere.example "20330525 03:33:20"
elsewhere.example.com "20330727 03:33:20"
```

Each non-comment line records one host that was seen answering with a
`Strict-Transport-Security` header, together with the expiry
(`"YYYYMMDD HH:MM:SS"`, UTC) of the remembered policy; a leading `.` before
the hostname means the policy covers all subdomains. A cache file with real
entries in it is the starting point for every reproduction in this task.

## The problem

A server that sends a `Strict-Transport-Security` response header with an
**extremely large `max-age`** — anything far beyond the roughly two-year cap
that browsers apply — makes curl **destroy the entire on-disk HSTS cache** it
maintains. Concretely:

- After the request finishes and curl writes the cache back to disk, the
  cache file is **truncated to zero bytes**: every previously remembered
  host is forgotten, and the current server is not recorded either.
- One such response disables the user's HSTS memory entirely until the cache
  is rebuilt from scratch.
- The value does not even need to overflow anything — it just needs to be
  larger than what the cache file's date formatter can represent. (Sending
  `max-age=1152921504606846976`, two to the power 60, is one such value.)

This is deterministic: any response carrying an extreme `max-age` triggers it,
regardless of the server, the URL, or the rest of the headers.

The correct behaviour — which the upstream project later adopted, and which
matches what browsers do — is:

1. the `max-age` value in a `Strict-Transport-Security` header is **capped at
   two years**: requesting 2^60 seconds must behave exactly like requesting
   `2*365*24*3600` seconds,
2. an entry whose expiry cannot be turned into a calendar date must be
   **skipped, not fatal**: the rest of the cache is still persisted, the
   current server is still recorded, and no previously cached host is lost,
3. the numeric `max-age` is never stored raw; it is always converted to an
   absolute expiry that fits the cache file's date format.

Your job:

1. reproduce the cache destruction with the recipe below,
2. localise and **fix the real bug in the source tree** — the fixed tree must
   keep building with the project's own build system, with the fix at the
   root cause rather than a workaround,
3. rebuild the binary so the fixed behaviour is in `/app/src/src/curl`,
4. write up the root cause in `/app/diagnosis.md`.

## Reproducing

Start a throwaway loopback HTTP server that answers any GET with a
`Strict-Transport-Security` header carrying `max-age=1152921504606846976`
(there is no external network, but loopback works):

```sh
python3 - <<'PY' &
from http.server import BaseHTTPRequestHandler, HTTPServer
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        body = b'-foo-'
        self.send_response(200)
        self.send_header('Date', 'Tue, 09 Nov 2010 14:49:00 GMT')
        self.send_header('Content-Length', str(len(body)))
        self.send_header('Connection', 'close')
        self.send_header('Strict-Transport-Security', 'max-age=1152921504606846976')
        self.end_headers()
        self.wfile.write(body)
    def log_message(self, *args):
        pass
HTTPServer(('127.0.0.1', 8891), H).serve_forever()
PY
```

Seed a cache file and make one request against it:

```sh
cat > hsts_in <<'EOF'
# Your HSTS cache. https://curl.se/docs/hsts.html
# This file was generated by libcurl! Edit at your own risk.
somehere.example "20330525 03:33:20"
elsewhere.example.com "20330727 03:33:20"
EOF
CURL_HSTS_HTTP=yes CURL_TIME=1920582000 \
  /app/src/src/curl -s -o /dev/null --hsts ./hsts_in \
  --resolve this.hsts.example:8891:127.0.0.1 http://this.hsts.example:8891/
wc -c < hsts_in
```

Observations at the current tree state:

- `wc -c < hsts_in` prints **`0`**: the request destroyed the whole cache.
  Both previously cached hosts are gone and the server that just sent the
  policy is not recorded. (The command itself exits `0` — the damage is in
  the file.)

Expected behaviour after your fix:

- `wc -c < hsts_in` prints a non-zero size, and the file contains all three
  entries: the two original lines exactly as they were, plus a new line for
  `this.hsts.example` whose expiry is exactly two years after the fixed
  clock reading — with `CURL_TIME=1920582000` the line must read

  ```
  this.hsts.example "20321109 23:00:00"
  ```

  (Note that the remembered expiry is capped: it is the two-year cap after
  the current time, not 2^60 seconds from now, which the date format cannot
  even express.)

Notes:

- `CURL_HSTS_HTTP=yes` and `CURL_TIME=...` are environment overrides that
  only the debug build honours — that is why the checked-in build is a debug
  build. `CURL_TIME` pins the "current time" used for HSTS bookkeeping to a
  deterministic value so the capped expiry is exact; change the value and the
  capped date moves with it.
- the fix belongs in the tree, not in the command line: do not make the
  reproducer pass by wrapping the binary, disabling HSTS, pre-truncating or
  rewriting the cache file, or any other workaround that would leave the
  shipped binary still destroying caches.
- a fix may not paper over the symptom (e.g. by deleting the cache-writing
  code path, weakening the build, or turning checks off).
