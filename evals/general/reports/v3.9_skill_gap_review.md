# v3.9 skill coverage review

Reviewed the 785-task suite at `evals/general/tasks` against the published v3.9
records on `eewer/general-agent-bench-results` (all 4,710 `reward.txt` files
fetched, plus `summary.json`, `results.json` per pair, and the audit bundle).

Every number below is measured from the tree or the published records, not read
off `WORKFLOW.md`. Where a keyword scan could produce a false positive I checked
the hit; two notable ones are called out in the text.

The dominant idiom is narrow. 72 tasks deliver literally `/app/solve.py`, 54
deliver `/app/answer.json`, 44 deliver both. 151 instructions explicitly demand
a reusable general tool, 492 mention hidden cases, 84 say "self-contained". The
canonical task is: read fixtures, write one Python program, emit a JSON report
with an exact schema, verifier re-runs the program against hidden fixtures.

That is a good shape for a benchmark and a poor match for how the work usually
looks.

## 4. Real-world alignment

Three measured facts drive most of the gap.

The environments are empty. Median shipped files in `environment/files` is 1.
599 tasks ship 3 or fewer. 142 ship none at all. Median shipped source lines of
code is 0, p95 is 233, max is 1,137 (`dusk-wicket`, 5 files). Only 52 tasks ship
200 or more lines. Only 2 ship 1,000 or more. Even among the 167 tasks I
classified as touching shipped source, the median is 163 lines for repair and 117
for extension.

Nothing ships a repository. Zero tasks have a `.git` directory in
`environment/files`. Eight build one inside the Dockerfile (`fern-hearth`,
`hollow-keystone`, `vine-mantle`, and five `v1-skill-*` git tasks). No agent ever
runs `git log`, `git blame`, opens a PR, resolves a conflict against a moved
main, or works out which of 40 modules owns a behaviour.

The resources are flat. 755 of 785 tasks get 1 CPU. 617 get 2 GB. Median agent
timeout is 1,200 seconds. Only 32 tasks score 2 or more on the rubric's
`resource_pressure` dimension. Nothing is big enough to force chunking,
streaming, spilling, caching, or a cost decision.

The rubric itself reports three dead dimensions across the 515 measured tasks:

| Dimension | Score 0 | Score 2+ | Mean |
|---|---|---|---|
| `unsafe_action_penalty` | 472 | 11 | 0.10 |
| `resource_pressure` | 414 | 32 | 0.27 |
| `interaction_statefulness` | 379 | 43 | 0.36 |
| `tool_breadth` | 159 | 174 | 1.14 |
| `debugging_ambiguity` | 108 | 161 | 1.13 |
| `hidden_case_generalization` | 0 | 356 | 1.92 |

`hidden_case_generalization` is scored 1+ on all 515 tasks. That is the suite's
centre of gravity and it is a benchmark property, not a work property.

Instructions are also fully specified. Median length 4,098 characters, p90 8,063,
max 14,267. They name exact paths, exact schemas, exact key order, exact numeric
formats. No task presents an incomplete requirement and asks the agent to make
and defend a judgement call, which is a large share of real work and the thing
agents most often get wrong.

Network is off. All fixtures are local. No task requires reading real
documentation, calling a real third-party API, handling a rate limit, an auth
failure, a schema change upstream, or a version that no longer resolves.
`v1-skill-web-research` is the closest thing and it does not hit the network.

## 5. Structural risks

427 of 726 competencies, 59%, are covered by exactly one task. The
tasks-per-competency histogram is 427 singletons, 215 pairs, 49 triples, 27
quads, and 6 tasks with five or more. A singleton claim rests on one verifier and
one fixture set, and `WORKFLOW.md` already documents four verifiers that were
vacuous, three that scored 1 on an untouched container, and 28 tasks whose own
reference solution could not pass. Single-task competencies are where the next
one of those hides.

291 tasks claim no competency at all: the 270 `v1-*` and the 21 supplementary
skill tasks. They are exempt from the clean-room contract lint and the
competency-claim gates by design. They are also the saturated half of the suite.

## 6. What to add, in priority order

Ranked by how much real work each one covers and how little the suite has of it.

1. Work inside an existing repository of realistic size. Ship 5k to 50k lines
   across 50 to 500 files with a `.git` history, a build, and a test suite. Ask
   for a change whose correct location is not named in the instruction. Verify by
   running the shipped suite plus hidden cases. This is the single largest gap
   and nothing else on this list substitutes for it.

2. A second language family. Go, TypeScript, Rust, and Java each deserve a base
   image and 20 to 40 tasks covering the ordinary work: a REST service with
   middleware, a CLI with subcommands, an ORM or query layer, a concurrency bug,
   a dependency upgrade with breaking API changes, a build that fails on one
   platform. 81% Python is a measurement of the suite, not of agent capability.

3. Frontend work. React or Vue component tasks with a bundler, a router, state
   management, CSS layout, accessibility checks, and a headless browser
   assertion. Zero CSS files in 785 tasks is a hole you can see from space.

4. Multi-service systems. A stack the agent actually brings up, with three or
   more services, where the task is to trace a request across them, fix a version
   skew, repair a health check, or run a migration without downtime. No task
   currently runs compose or Kubernetes. `amber-engine` is the closest shape: four
   Flask microservices the agent talks to but does not deploy.

5. CI/CD that runs. Author or repair a GitHub Actions or GitLab CI pipeline whose
   stages the verifier executes. One task sanitizes a workflow YAML. None builds
   one.

6. Real datastores. Postgres beyond four compose files, plus MySQL, MongoDB, and
   Redis, covering schema migration, index and query-plan work, connection
   pooling, replication lag, and a data fix that must not lose rows.

7. Streaming and messaging. Kafka or RabbitMQ with consumer groups, retries,
   dead-letter handling, ordering guarantees, and idempotent consumers. One MQTT
   task exists.

8. Debugging with reproduction cost. Intermittent failures, flaky tests, a race
   that manifests 1 time in 20, a memory leak under load, a performance
   regression across a commit range. `sable-journal` does the race case.
   `debugging_ambiguity` averages 1.13 out of 3 and only 15 tasks are categorised
   `debugging`.

9. Under-specified requirements. Instructions that omit a decision the agent must
   make, with a verifier that accepts a defensible choice and records what was
   chosen. Also the opposite case: a request that should be pushed back on.

10. Safety and irreversible actions. The `unsafe_action_penalty` dimension is 0 on
    472 of 515 tasks. Add tasks with a destructive path available: a production
    namespace, a `DROP TABLE`, a force push, a `rm -rf` one glob away, a live
    deploy. Score whether the agent did the irreversible thing without a reason.

11. Resource pressure. Tasks whose fixture is large enough that a naive
    load-everything solution OOMs at the declared 2 GB, or slow enough that a
    quadratic solution misses the timeout. 32 tasks currently qualify.

12. Third-party reality. A task with the network on, against a real or faithfully
    mocked external API, where the agent must read the docs, handle a 429, an
    auth error, and a changed response shape.

13. Cloud and infrastructure as code. Terraform plan and apply against a local
    provider, IAM policy that is too broad, an S3 bucket made public by accident,
    a cost anomaly in a billing export. `moto` covers a sliver of this today.

14. Observability. Prometheus scrape config and PromQL, a Grafana dashboard as
    code, structured logging and OpenTelemetry spans, an alert that fires on the
    right condition and not on the wrong one.

15. LLM application work, which is what most agents are now used for. RAG over a
    document set with retrieval quality thresholds, tool-calling against a schema,
    prompt versioning with an eval harness, token and cost budgets, serving a
    local model with vLLM or llama.cpp, quantization with a measured quality
    trade-off. The suite has strong coverage of training and tensor internals and
    almost none of building an application on top of a model.

16. Second-task coverage for the 427 singleton competencies, starting with the
    ones whose task is also in the never-passed or saturated band, where the
    single record carries the most weight and says the least.
