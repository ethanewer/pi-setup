# granite-anchor — the state-space search & serialization rig

You are the data-lab engineer for **Merce-Fountain**, a company that models
how knots of a water-distribution mesh rearrange. You are given one directed
**state-space graph** (nodes are gate configurations; each has a small **board**
representation; a directed edge means "one turn can reach this configuration").
Your job is to search that graph with a deterministic breadth-first search and
serialize every meaningful trace of it to a fixed set of files on disk.

Everything runs in one container. Work only inside `/app`; never modify
`/tests` or anything outside `/app`.

---

## The scenario / config file

`/app/config.json` describes the primary search. It has this shape:

```json
{
  "start": 0,
  "goal": 5,
  "nodes": {
    "0": {"rows": ["abc", "def"]},
    "5": {"rows": ["dcf", "abe"]}
  },
  "edges": {
    "0": [1, 2],
    "2": [4, 5]
  }
}
```

- `start` and `goal` are node ids (integers). `start` always exists as a key in
  `nodes`; `goal` may be absent from the reachable component (see edge cases).
- `nodes` maps each integer node id to a **board**: `rows` is a non-empty list
  of strings (the row-string representation of that gate configuration). Order
  within `rows` matters.
- `edges` maps each integer node id to a list of integer child ids it can turn
  into (directed edges). The list order in the JSON is **not** significant.

**Search rule (BFS).** Breadth-first search from `start`. Process each node's
children in **ascending integer order**. The **depth** of a node = its shortest
path length from `start`. A node is claimed the **first** (shallowest) time it
is reached and that depth is frozen; later/duplicate/shallower-overwrites never
change it. Edges that point to a node id that does **not** exist as a key in
`nodes` (dangling edges) are silently ignored. Self-loop edges (a node listing
itself) and duplicate edges (the same child twice) are ignored — the child was
or is claimed once.

`goal` is not required to be reachable from `start`.

## Deliverables

Write a single program `/app/search.py` (Python 3) that reads a config and
emits the artifacts below, then **run it** on `/app/config.json` so the files
exist at `/app`:

```
python3 /app/search.py           # = /app/config.json -> /app
python3 /app/search.py <CONFIG>  <OUTDIR>   # re-runnable on any graph
```

So: with no arguments it reads `/app/config.json` and writes into `/app`;
with two arguments it reads the given config and writes into the given output
directory (which it creates if needed). Never modify `/app/config.json`.

Every artifact is generated by running the mandatory search and exported to the
requested output directory:

#### (a) per-depth frontier files — `frontier_<depth>.txt`
For each depth `d` from `0` up to the greatest measured depth `D`, write
`frontier_<d>.txt` containing exactly the integer node ids at depth `d`, one per
line, **ascending integer order**. `frontier_0.txt` always exists (it holds
`start`). `D` is the depth of the deepest reachable node.

#### (b) checksum sidecar — `frontier.sha256`
One line per depth `d`:
```
<hex-sha256-of-that-frontier-file's-bytes>  frontier_<d>.txt
```
(two spaces before the filename). The hex digest must equal the real SHA-256 of
the `frontier_<d>.txt` you wrote, byte for byte. Newline-terminate the lines.

### (c) depth summary — `depth_summary.txt`
CSV with a header row `depth,count` and one row per depth `d = 0..D`:
```
depth,count
0,1
1,2
...
```
`count` = number of reachable nodes whose depth is exactly `d`.

### (d) move trace — `move_trace.json`
`{"boards": [...]}` whose `boards` is a **non-empty** list tracing the exact
shortest path from `start` to `goal`: first board is `start`'s rows, all
intermediate boards in order, last board is `goal`'s rows. Each board is the
row-string list `rows` of the corresponding node (`["abc","def"]` style). If
`goal` is unreachable, `boards` is just `[start's rows]` (a single board, still
matching the starter). Every board must be a list of strings.

### (e) DAG edges — `dag_edges.csv`
The **BFS search tree** as a two-column CSV with header `from,to`. For every
reachable node `v != start`, one row `from,to` where `from` is the node that
**first discovered** `v` in the BFS (its parent, at depth one less) and `to`
is `v`. Rows sorted ascending by `from`, then by `to`. These edges are the
"parent" orientation of the DAG formed by the search.

## Behavior on edge / malformed inputs (hidden cases probe these)

1. **Unreachable goal.** If `goal` is not reachable from `start`, produce all
   fronters / checksums / summary / dag edges for the *reachable component*
   normally, and emit `move_trace.json` whose `boards` is just the start board.
   (Reachable component = nodes discovered by the BFS.)
2. **`start == goal`.** The trace has exactly one board: `start`'s rows
   (`boards == [start's rows]`). Neighbors are still explored, so fronters,
   summary and dag edges behave as usual.
3. **Orphan edge targets** (an `edges` child id not present as a key in
   `nodes`): ignore them — they are not traversed and never appear in any
   `frontier_*.txt`, summary, dag CSV or trace.
4. **Duplicate edges and self-loops**: ignored; each node appears exactly once
   (at its shallowest depth).
5. **Node ordering**: all frontier files, the summary rows, and the dag edge
   rows use **ascending integer** node-id order. Node ids are integers; do not
   sort them as text ("10" strictly after "2").
6. Deterministic regardless of the config's `edges` list order and JSON key
   order. Parent assignment follows BFS first-discovery (a node's parent is the
   node that reached it first, processing each parent's children ascending).

Any node id appearing in edges or as start/goal is an integer; the value in
`rows` is always a list of strings. You may assume every config is well-formed
JSON with these types (no need to defend against a non-JSON or type-broken
file).

## Verification contract (what the checker insists on)

A hidden checker re-runs `/app/search.py` on four unseen graphs and compares,
for each, every artifact structurally equal to an independent re-derivation of
the BFS; it also re-checks the `/app` outputs. Correctness therefore requires:

- exact per-depth frontier member sets & ordering;
- sha256 of each `frontier_*.txt` equals its line in `frontier.sha256`,
  including the bytes on disk;
- `depth_summary.txt` header and exact rows;
- `move_trace.json` with a non-empty `boards`, first board == starter rows and,
  when reachable, last board == goal rows and the whole list equal to the BFS
  shortest path;
- `dag_edges.csv` with exactly `from,to`, every parent->first-discovery
  row, sorted.

Everything must run on a single container with no network access at runtime and
no GUI. Costs do not matter; keep within 300s.
